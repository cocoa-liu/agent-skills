# Code Reading Guide

目标是让读者能独立解释和维护代码。先给职责和执行过程的轮廓，再展示细节；不把文件清单或逐行翻译当作导读。默认沿用用户语言和现有阅读水平。用户只要求聊天跟读时，每轮讲一个关键逻辑块并等待回答，不强行生成 HTML。

## 1. 先确认真实范围

- 阅读适用的 AGENTS.md、仓库状态、diff 和关键上下文。PR 固定 base 与 head；base 使用 PR 与目标分支的 merge-base，避免把目标分支后来增加的代码误算成 PR 改动。优先使用本地 Git 或已连接的代码平台；只有链接且尚未取得代码时先获取内容。
- 沿入口、调用者、回调、注册/工厂、配置、核心实现、结果返回及必要测试追踪调用链。只看 diff 无法解释的调用方要继续读；明确哪些来自本次修改、既有框架或外部依赖。
- 区分启动时、每次请求/迭代、后台异步与清理阶段。数据经过 A→B，不代表直接调用顺序就是 A→B；特别解释控制反转、回调和惰性执行。
- 记录具体快照。生成器默认读取指定 Git commit，**不会读取未提交修改**；要讲工作区改动时显式使用 `--working-tree`，展示文件摘要，不能冒充已提交版本。
- 用户已指定重点、顺序、目录或学习目标时沿用。缺少范围且无法从环境判断时，问一个简短问题，同时继续可独立开展的阅读。文档任务默认不改被讲解的源代码，也不自动提交或发布文档。

## 2. 先写讲解骨架，再做页面

先用一个贯穿例子说明：输入是什么、原先有什么问题/限制、现在会发生什么。整个仓库没有 PR 时，说明这套代码解决的实际任务，不虚构“改动前”。

按执行流程组织逻辑块，数量由代码复杂度决定。通常先介绍整体职责，再讲初始化与依赖、输入构造、核心执行、输出、维护；只保留这次任务需要的环节。文件可能在多个逻辑块出现，不能按文件名或 diff 顺序机械讲解。

每个逻辑块回答：

1. 这块在整条流程中做什么，为什么需要它。
2. 谁调用它，何时调用；输入输出的具体类型、值、状态或形状是什么。
3. 陌生概念的最小例子，然后回到当前实现。
4. 按推荐顺序展示**实际代码片段**和准确文件/行号。每个片段都给调用者、输入输出、作用、例子、按逻辑分组的行号说明和简短理解检查；不能只给源码链接。
5. 一个需要维护者理解的边界：不变量、状态生命周期、异常、精度、资源或副作用。不要为每段凑风险清单。
6. 一个短问题。答错给更小的例子，答对可展开更深入的维护解释；由读者主动继续。

读者在后续对话中提交答案或导出的笔记时，先定位他误解的概念，再调整解释深度；不要直接重复原讲解或跳到下一页。

作者意图只有在注释、设计记录等证据支持时才当事实。否则标成推测并说明依据。发现可以更简单的实现，说明具体简化、代价与需要的验证；不为了讲解直接重构项目。

## 3. 用一组具体数据贯穿执行

逐步记录同一输入的中间状态与最终输出，并标注每一步是**实测、由代码推导、历史结果或假设**。推导例子也可以完整，但不能说成运行过。

特别区分逻辑有效数据与物理布局，例如长度/容量、有效行/padding、token/字、请求数/批量、逻辑索引/实际地址。性能数据同时注明环境、配置、计时范围、预热和样本；页面能渲染不证明模型或业务实现通过测试。

复用已有验证证据，只补充解释所必需的轻量实验。不要为了生成文档自动启动昂贵训练、全量基准或占用加速卡。未获得或未执行的验证明确写出。

## 4. 生成离线 HTML

阅读 [references/guide-data.md](references/guide-data.md) 编写 `guide.json`。使用随 skill 提供的通用模板与构建器，不把上一个项目的脚本、路径、代码、指标或固定章节数复制过去。

```bash
python <skill-dir>/scripts/build_guide.py \
  --repo /path/to/repository --revision <head-commit> --base <base-commit> \
  --spec /path/to/guide.json --output /path/to/code-reading-guide.html
```

整个模块导读可省略 `--base`；讲未提交代码时加 `--working-tree`。`refs[].version="base"` 可展示被删除或替换的旧实现。PR 模式会自动收集 base→head 的所有改动文件，不以讲解 refs 过滤；普通模块导读只嵌入引用的文件。生成前检查要嵌入的完整 diff / 源文件，避免把凭据或无关私密内容放进文档。

页面默认提供：

- PR 模式首先展示“PR 阅读进度”：采用类似 GitHub 的文件树、差异代码区和独立右侧批注栏。阅读页使用窗口宽度，章节导航收为顶部栏；文件树和批注栏可收起。代码保留缩进、旧/新行号与增删标记，提供离线语法高亮、横向滚动和可选换行。
- 列出全部新增/删除代码及上下文，灰色为未读，绿色为已理解，黄色为疑问/暂缓。支持直接拖选代码文字、按新/旧行号输入范围、Shift 连选、整段或整文件批量标记，并显示已选行数。选择动作保留原生文本复制能力，上下文不计入阅读进度。
- 每个文件分别记住当前可见的代码行、行内偏移与横向滚动位置。切换文件再回来、刷新或重新打开时恢复位置，批注栏同步跟随；第一次打开的文件从开头显示。位置随阅读进度自动保存，并包含在 JSON 和带标记 HTML 备份中，兼容没有位置字段的旧记录。
- 右侧默认完整展开当前文件所有已有批注，可直接编辑。每条只显示内容，去掉标题、状态选择和卡片留白；空批注和短批注默认一行，长内容自动换行增高，删短后自动缩回。阅读状态使用代码区的标色按钮修改。
- 桌面端将批注第一行文字与对应代码行水平对齐，代码与批注双向同步滚动；只在内容需要时增加对应行的展示高度，避免相邻批注重叠。有批注的代码行常态保留蓝框，悬停或编辑时加强提示；用箭头、联动高亮和批注栏顶部的行号提示标明当前对应行，悬停或编辑时也更新指示。窄屏保留完整列表，不挤成三栏。
- 点击尚无批注的代码行或批注气泡可添加批注。二进制、重命名和文件属性变化也须列出，不伪装成文本行。布局调整只影响展示，不能改动源码文本或阅读状态。
- 整体职责图和输入/结果示例；执行顺序的导航。
- 每次一个逻辑块，代码片段默认折叠，源码弹窗按行定位。
- 一条输入的数据旅程、概念最小例子、理解检查与自述笔记。
- 按“症状→责任块→检查→验证”组织的维护入口。
- 无外部字体/CDN/网络依赖，移动端可用；按内容快照隔离的进度保存与 JSON 导出。

阅读标记按独立的代码快照 ID 保存，不能绑定会随讲解文案变化的页面指纹。布局或语法高亮更新也不能改变既有行标识和进度键。自动保存到本浏览器，并提供 JSON 导出/导入以及“保存带标记的 HTML”；导入须先完整校验快照和所有记录，不兼容时不能部分覆盖。对存储失败必须明确提示，不能显示“已保存”。不要把本地阅读进度说成云端同步或自动回写原 HTML 文件。

可根据项目增减交互，但不要让动画、页面数量或装饰压过学习内容。文本由构建器安全编码；讲解字段是纯文本，不插入原始 HTML。截图和临时验证文件放在工作区外或用户指定的产物目录。

## 5. 检查后交付

构建器会拒绝不存在的路径、越界行号、缺少讲解的代码块和错误的导航/答案索引。它只能检查结构，**仍要核对行号对应的代码确实支撑文字结论**。源码变化后重新阅读和生成，不用盲目的行号偏移代替语义复核。

有 Playwright 时运行通用浏览器检查：

```bash
node <skill-dir>/scripts/check_guide.cjs /path/to/code-reading-guide.html \
  --out /path/to/browser-check
```

若 Playwright 装在其他位置，可用 `CODE_READING_PLAYWRIGHT=/path/to/node_modules/playwright` 指定；没有浏览器能力时报告仅完成静态检查，不能声称交互已验证。检查覆盖逐块导航、题目反馈、源码定位、笔记、导出、手机布局和零外部请求。有 PR 差异时，上面的检查还会调用 `scripts/check_review.cjs`：验证灰/绿/黄、批量标记、右侧批注、刷新与浏览器进程重启恢复、文案更新不丢标记、JSON 导入/导出、不同代码快照拒绝导入，以及带标记 HTML 在全新浏览器环境下恢复。实际看一下桌面/手机截图，不只相信测试退出码。

交付 HTML 的可点击路径和简短使用方式；说明同一浏览器自动恢复，换浏览器/移动文件时使用备份或带标记 HTML。个人标记和测试批注保存在本地，不自动发布到文档仓库；注明源码快照及未验证的内容。仅在用户要求或已有明确授权覆盖当前文档时，复制到目标仓库、提交或推送。生成器、浏览器检查与 skill 本身需要维护时可运行 `python <skill-dir>/scripts/test_build_guide.py`，不要把这些工具测试说成被讲解项目的测试。
